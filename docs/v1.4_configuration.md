# v1.4 — Configuration

Everything Theater knows about the machine it runs on is currently a Python
constant. This release moves the parts a user legitimately needs to change into
`$THEATER_HOME/config.toml`, and — the large half of the work — makes it
possible to teach Theater a harness it has never heard of without editing the
source tree.

Three decisions apply to the whole release and are not revisited per feature:

**Unknown keys are a loud error.** A typo'd key that is silently ignored is the
same defect class as the v1.2 schema no-op: the user believes they configured
something, the daemon disagrees, and nothing says so. Every table is validated
against a known key set and an unknown key aborts daemon start with the file
path, the key, and the closest legal spelling.

**Machine-scoped only.** There is no project-local `.theater/config.toml`.
Theater's whole model is one daemon per machine holding one registry; a
per-project config would mean the harness set depends on which directory the
daemon happened to start in, which is not a property the daemon has.

**No hot reload.** Config is read once at daemon start. `theater restart` to
apply. This is stated in the CLI help and the docs rather than inferred,
because a config edit that appears to do nothing is worse than one that
requires a documented restart.

Explicitly **not** configurable: the default approval mode. `harness/base.py:80`
records why — there is deliberately no default anywhere, because the choice is
the whole safety story for a child nobody is watching. A config key setting it
to `yolo` once and forever defeats that by design, not by accident.

## 1. The config layer

`$THEATER_HOME/config.toml`, parsed with stdlib `tomllib`. **Read-only**:
Theater never writes this file. Writing TOML would need a third-party
serializer, and a config the tool rewrites is a config whose comments and
ordering die on first write.

```
theater/config.py        load, validate, defaults, source tracking
theater/paths.py         + config_path()
```

The loaded object is passed explicitly from daemon start-up into the components
that need it, rather than being read from a module-level singleton. Two
processes read this file (daemon, CLI) and tests relocate `$THEATER_HOME`
constantly; an import-time global would bake in whatever `$THEATER_HOME` was
set at import.

CLI surface:

    theater config          resolved values, each tagged with its source
                            (default / config.toml / plugin)
    theater config path     the file to edit, whether or not it exists

`theater config` prints the *resolved* view, not the file. The failure it is
built to diagnose is "I set the key and nothing happened", which requires
seeing the value the daemon actually holds and where it came from.

Effort: 3–4 h.

## 2. Declaring a harness from config

> **Superseded.** 2a shipped and was then removed in the same release; see step
> 7 under Order for why. What survives is 2b (a plugin may set
> `has_transcript = False` and end its turns on the screen), 2c (plugins, now
> the only mechanism) and 2d (the `harnesses` RPC). Kept as written because the
> investigation below is still the reason the injection modes exist.

The heart of the release. Today a harness is a Python class implementing six
abstract methods. Of those, two are pure data (`plan_launch`, `is_idle_screen`),
two are nearly data (`find_transcript`, `session_id`), and two are not data at
all (`parse`, `native_children`).

So there are two tiers, and both ship.

### 2a. TOML-declared harness

Covers spawn, send, presence, icon, `theater harnesses`, unmanaged-pane
detection. A `DeclaredHarness` class implements the `Harness` ABC by reading a
dataclass built from TOML.

Investigation of the two harnesses the user actually has installed changed this
schema. MCP injection is not the two-way choice v1.3 assumed:

| Harness  | Lever                                              | Per-session |
|----------|----------------------------------------------------|-------------|
| vibe     | `VIBE_MCP_SERVERS` env var                         | yes         |
| claude   | `--mcp-config=<path>` file                         | yes         |
| codex    | `-c mcp_servers.theater.command=…` argv, TOML-valued | yes       |
| opencode | `opencode mcp add`, global `opencode.json` only    | **no**      |

Two consequences.

**A third injection mode, `argv`.** Codex takes dotted TOML overrides as
repeated `-c key=value` flags. This is neither env nor a written config file,
and no amount of stretching the other two covers it.

**A setup step, not just a spawn template.** OpenCode has no per-invocation MCP
flag at all, so the participant id cannot be baked into the MCP server's argv
the way `harness/base.py:24` requires. The only route is a one-time global
registration whose args contain OpenCode's own `{env:THEATER_ID}` placeholder,
resolved per pane by the env var Theater already sets. That would be a `theater
setup <harness>` command emitting the registration, plus a `global` injection
mode that asserts the setup was done and fails loudly if not.

**Deferred, not built.** `global` and `theater setup` are out of v1.4. Both are
specified entirely by OpenCode behaviour that cannot be checked here: OpenCode
has never been run on this machine, has no config directory yet, and keeps
sessions in a database rather than JSONL. Shipping a mode whose only user is a
harness whose behaviour is guessed would be shipping a guess with a config key
attached. OpenCode remains declarable through `mcp_file`, which writes a config
per spawn — if that turns out not to work, the `global` mode is the fix and the
failure will have told us what it must do.

**What replaced the `injection` enum.** Three independent slots, not one mode:
`mcp_env` (vibe), `mcp_argv` (codex), and `mcp_file` + `mcp_file_argv`
(claude). A harness may fill any combination. This is strictly more general
than the enum, and it removes the question of what an enum value means when a
harness needs two of them at once.

Substitution is literal `str.replace`, not `str.format`: `mcp_file` contents
are JSON, and `{"mcpServers": …}` under `str.format` raises. Placeholders are
`{id}`, `{prompt}`, `{binary}`, `{theater}`, `{config_path}`.

Argv order is fixed rather than templated — `binary`, approval flags,
`mcp_argv`, `mcp_file_argv`, `argv`. It is the only order where flags precede
the positional prompt, and it matches what both built-in adapters already do.
An argv element that renders empty is dropped, so `argv = ["{prompt}"]` with no
prompt launches an interactive session rather than passing `""`.

`binary`, `approvals` and `idle_prompts` are required. Each missing value
misleads rather than degrades: nothing to run, a `yolo` spawn with no flags
that looks deliberate, or no turn that ever ends and so every caller hangs. All
three approval modes must be spelled out, the empty list included.

A declaration may not take a built-in's name. It would silently lose transcript
parsing, which is the difference between a read turn boundary and a guessed
one; the error says to pick another name or write a plugin.

```toml
[harness.codex]
binary       = "codex"
icon         = "◇"
aliases      = ["codex-cli", "openai-codex"]
idle_prompts = ["›", "▌"]
mcp_argv     = ["-c", "mcp_servers.theater.command={theater}",
                "-c", 'mcp_servers.theater.args=["mcp","--id","{id}"]']
approvals    = { manual = [], edits = ["--full-auto"], yolo = ["--dangerously-bypass-approvals-and-sandbox"] }
```

Effort: 4–6 h. **Done.**

### 2b. Screen-derived turn end

A declared harness has no `parse`, and `parse` is what produces `turn_end` —
which drives status, the bus, *and job completion*. Without it a declared
harness accepts `theater_send` and then hangs the caller's `await_sessions`
forever. That is not a hypothetical: it is a failure this project has already
shipped and fixed once.

So for declared harnesses only, the AWAITING_INPUT screen heuristic
(`is_idle_screen` over `capture-pane`) is promoted from a display hint to a
completion signal. This inverts its documented risk profile — it was tuned to
accept false negatives — so it is scoped strictly to harnesses that have no
transcript parser, and it needs a faster poll than the existing
`AWAITING_INPUT_TIMEOUT = 10.0`.

Risk: medium. A false idle finishes a job early and the caller reads a partial
answer. Mitigated by requiring the idle prompt to hold across two consecutive
polls, and by never applying this to a harness that has a real parser.

Built as `Observer._watch_screen`, selected per participant by
`Harness.has_transcript`. Three details settled while building it:

- An unreadable screen decides nothing. A failed `capture-pane` is not evidence
  of either state, so the status is left exactly as it was rather than being
  read as silence.
- `IDLE_CONFIRMATIONS = 2`. One would let a pane cleared mid-work finish a job.
- The turn-end bus event carries `source: "screen"` and `index: -1`. It came
  from no transcript record, and nothing downstream should be able to mistake a
  rendering for a parsed message.

Effort: 2–3 h. **Done.**

### 2c. Python plugin harnesses

`~/.theater/harnesses/*.py`, imported at daemon start. Each module exposes
`HARNESS = MyHarness()` implementing the full ABC. This is the escape hatch for
anyone who needs real transcript parsing — Codex, if its rollout JSONL turns out
to be clean, deserves a real adapter rather than a declaration.

**This is the piece that gets the documentation.** `docs/harness-plugins.md` is
a first-class deliverable of this release, not a footnote: the ABC, each method
with what "return nothing" means, a complete worked example, and how to test a
plugin without spawning anything.

Four decisions settled while building it:

- Loaded **by path** under a synthetic module name, never by putting the
  directory on `sys.path`. On the path, a user's `json.py` shadows the standard
  library for the whole daemon and the resulting failure names neither the file
  nor the plugin system.
- **A plugin may replace a built-in; a declaration may replace neither.** A
  plugin is a full adapter and can do everything the built-in did. A declaration
  cannot parse a transcript, so the same move would silently downgrade turn
  detection from a record to a guess.
- Failure is loud and start-up stops, with the file path in every message. The
  soft-fail alternative reproduces exactly the defect this release exists to
  remove: a harness the user believes they installed and which is quietly absent.
- Alias collisions are refused rather than resolved by load order, for both
  plugins and declarations — "whichever file sorts first wins" is not debuggable
  from the symptom, which is an agent observed as the wrong harness or not at all.

The doc's worked example is not illustrative pseudocode: it is extracted from
the file and executed, and every assertion in its testing section is run.

Effort: 1–2 h code, plus the doc. **Done.**

### 2d. Registry consequence

`HARNESSES` is a module-level dict built at import (`harness/__init__.py:32`),
read directly by `regie/palette.py:22`, `cli.py:34`, `daemon/methods.py`,
`daemon/observer.py`, `daemon/harness_detect.py`. Once the set comes from
config, three processes parse that config independently and can disagree — the
régie offers a spawn the running daemon rejects.

Fix: the daemon grows a `harnesses` RPC returning name, icon, binary and
availability; the régie and CLI call it instead of importing the registry.
`HARNESSES` becomes a lazily-built registry inside the daemon process.

Effort: 1 h.

## Order

1. Config layer — everything depends on it — **done**
2. Constants (5) — proves the layer on low-risk values — **done**
3. Theme (3) and favourite (4) — small, visible — **done**
4. `harnesses` RPC (2d) — before the registry becomes dynamic — **done**
5. Declared harnesses (2a) + screen turn-end (2b) — **done, then removed**
6. Plugins (2c) + `docs/harness-plugins.md` — **done**
7. Plugins as the only mechanism — **done**
8. A codex plugin — **done**
9. Job rescue — **done**

Steps 7 to 9 were not in the original plan. What changed:

**Declarations were removed after being built** (step 7 undoing step 5). The
question that killed them: what does a declared harness actually get you that a
plugin does not, and the honest answer was "less, and worse". A TOML table can
describe launching a CLI but never reading its transcript, so every declared
harness ends its turns on a screen heuristic — a guess where a plugin has a
record. Offering it first steered users toward the weaker half of the system.
Worse, nothing that shipped went through the plugin loader, so the extension
point was exercised only by tests. Now the three shipped adapters are plugins in
`theater/harness/builtin/plugins/`, read by the same scanner as a user's, and
`[harness] disabled` is the only key left over the registry.

The shallow half survives where it is honest about itself: a plugin can set
`has_transcript = False` and get exactly the old declared behaviour, as a
property of an adapter rather than a second kind of adapter.

**A codex plugin** (step 8) replaced the unverified example declaration with a
real, verified adapter. Verified against five rollout files on this machine: 8
turn ends across them, `session_id` recovered from `session_meta` 5/5, and
`find_transcript` resolving by both cwd and session id. `turn_aborted` counts as
a turn end alongside `task_complete` — an abandoned turn still has to release a
waiting caller. One caveat that is not fixable from here: codex opens a trust
dialog on its first run in a directory, waiting on a keypress that no transcript
records, so a spawn there reads as WORKING until a human answers it.

**Job rescue** (step 9) came out of testing the above. A missed turn-end record
left the caller's `await_sessions` waiting forever, and the symptom the user saw
was a two-agent conversation dying on the second reply. A third quiet timer, at
60s, finishes a running job when the transcript has been silent that long over a
screen that looks idle, with the last thing the agent said as the result and
`error_code = "turn_end_unseen"` so salvage is distinguishable from a declared
reply. It needed its own clock: the screen check throttles itself by pushing its
own clock forward, so a rescue reading that clock would never come due.

Two details settled while building step 4, both worth keeping:

- `harness.describe()` is the single builder for the RPC, `theater harnesses`
  and the palette. The three had each been formatting the registry their own
  way, so a field added for one silently missed the others.
- Consumers fall back to their own registry when the daemon cannot answer,
  including when it answers `unknown_method` — a daemon that predates the
  method necessarily has the shipped set, so the local list is correct. Any
  other `RemoteError` propagates: a plausible-looking list is worse than a
  visible failure.

## Verification

The codex adapter is verified against real rollout files, as described above,
but has never been spawned end to end — the trust dialog stands in the way of an
unattended run. Its idle prompt string and its tolerance for the MCP injection
flags are read from its own `--help` and config surface, not observed.

OpenCode is installed here and deliberately untouched. Its session state is not
a transcript in the sense this system means, so it needs its own investigation
rather than a plugin written on the same afternoon. Deferred to v1.5.

What is verified: plugin discovery, load, rejection and precedence for both
shipped and local files; the shipped set failing loudly and a local file failing
softly; `[harness] disabled` matching a filename before import and a harness
name after; `theater harnesses` and `theater config` provenance; every parse
path in all three adapters; the screen turn-end loop against a fake pane; and
the rescue against an idle screen, a busy screen, an unreadable capture and a
participant with no pane.
