# v1.5 — OpenCode

A fourth shipped harness, and the first one whose output is not a file.

Every adapter before this one worked the same way: find the transcript the
session writes, hold a byte offset into it, parse each new line. OpenCode writes
no transcript. Every session on the machine lands in a single SQLite database,
`~/.local/share/opencode/opencode-stable.db`, and there is no file to tail and
no offset to hold.

That is why the release is two commits. The first makes such an adapter
expressible at all; the second is the adapter.

---

## 1. The seam (commit `e7b4d1d`)

Watching a session is two jobs that had been one lump of code inside the
observer:

```
job 1: get the text        job 2: decide what it means
────────────────────────   ──────────────────────────────
find the file              IDLE / WORKING transitions
open it, tail it           settling before IDLE is believed
follow a rotation          60s job rescue
skip to EOF on attach      dead detection, awaiting-input
```

Job 1 is harness-shaped. Job 2 is policy, and it is where every observation bug
in this project has been. So job 1 became a replaceable seam and job 2 did not:
`Harness.open_source()` returns a `Source`, the default being `TranscriptSource`
— the old inline tailing, moved out intact — and a plugin may return its own.

**Why not let a plugin bring its own observer?** Because the settling logic, the
rescue timer and the relocation timer took a dozen fixes to get right, and one
copy per harness means fixing them once per harness. The seam sits below the
policy, not around it.

Three fields of the `Batch` a source returns are load-bearing, and each exists
because of a specific failure:

- **`progressed` is not "produced events".** A bookkeeping record advances the
  input with zero events. Reading that as silence lets the rescue fire mid-turn.
- **`status` is for sources that can ask.** A file tail can only infer status
  from silence. A database can read it. When a source says so, the guessing is
  skipped for that participant.
- **`waiting=True` means "nothing to read from yet".** The observer then runs no
  timers at all, because a quiet timer against a source that has never spoken is
  measuring nothing.

Commit 2 added one more method to the interface: `history(last_n)`, the whole
session from the beginning with clipping off. `read()` is a tail and cannot
answer that — by the time an agent calls `read_transcript` for the full text of
a reply, the batch that carried it is long gone. `read_transcript` now goes
through the source instead of re-reading the file itself, which is what makes it
work for a harness with no file.

## 2. The adapter (this commit)

### Launching

`$OPENCODE_CONFIG` points at a config file that opencode **merges** into the
user's own rather than replacing. Verified with `opencode debug config`: model,
providers and seven pre-existing MCP servers all survived with `theater` added.
So the policy the other three adapters follow holds here too — register one
server, touch nothing else — and `~/.config/opencode/opencode.jsonc` is never
written, which matters because it is JSONC and a programmatic rewrite would take
every comment in it.

`opencode mcp list` inside a spawned session reports `theater ✓ connected`.

**`edits` degrades to `manual`.** OpenCode has one approval flag, `--auto`, which
is yolo; there is nothing between that and the default. The rejected alternative
was to write a `permission` block into the merged config — rejected because a key
this adapter has not verified against the running version takes the entire launch
down, and a spawn that asks twice beats a spawn that will not start.

### Observing

`event(aggregate_id, seq, type, data)` is append-only with a per-session
monotonic `seq`, which is a *better* cursor than a byte offset: it cannot land
mid-record. The database is opened `mode=ro`, never through `opencode db`, which
takes a write lock and fails with "database is locked" against a live session.
`immutable=1` is deliberately not set — it promises the file will not change,
which is the opposite of what a tail needs.

Four things in the event stream had to be handled exactly, and each was found by
driving a real session rather than by reading docs:

| Shape | Why it matters |
|---|---|
| `finish` fires twice per message, the second time with `time.completed` | Deduped by message id, or every reply lands on the bus twice |
| `finish == "tool-calls"` ends a *step*, not a turn | Treating it as a turn end resolves the caller's `await_sessions` at the first tool call, with an empty answer |
| Text parts arrive empty, then are *replaced* by the whole text | Streaming them would put four prefixes of one reply on the bus and resolve the job with whichever landed last |
| Tool parts go pending → running → completed | Pending has no arguments yet and may never run |

So assistant text is buffered per message and emitted once, at finish. The cost
is that a reply appears at the end of its step rather than as it is typed; tool
activity still streams, so a long turn is not silent.

`session.directory` is the *resolved* path — on macOS `/private/var` where the
caller says `/var` — so both sides get `Path.resolve()`. `parent_id IS NULL`
excludes sub-agent sessions, which share their parent's directory and would
otherwise win as the newest match.

`status` is reported only at attach, where the database can say something silence
cannot: whether the session we just found is mid-turn. After that the observer's
own policy runs.

### Known gaps

- **Sub-agents are visible but unreportable.** `session.parent_id` identifies
  them, but `native_children` is keyed by transcript path and there is no path
  to key on. The interface would have to change; nothing else here would.
- **`is_idle_screen` reads the footer**, matching `esc interrupt` for working and
  `ctrl+p commands` as proof the footer drew at all. It is a display hint feeding
  AWAITING_INPUT, never a control decision.

## Verification

The adapter was built against a live database, not a specification. A session was
driven through a question, a tool call and an answer; the source was attached,
rewound and drained; and the resulting event sequence was compared against what
`history()` returns for the same session. Both produce the same six events in the
same order.

`tests/test_harness_opencode.py` reproduces that database with a `Recorder`
fixture that writes the same four tables and the same event payloads, including
all four shapes in the table above — the fixture keeps the event log and the
message/part tables in step, because `read()` follows one and `history()` reads
the other, and a fixture that let them disagree would hide a bug in either.

What the tests cannot cover is the tmux half — a spawn writes a window, and
there is no way to assert on that from a test process. The launch plan is
verified by unit test (argv, env, and that the participant id is present in the
serialized plan); that the window comes up and the agent connects has to be
checked by hand:

```
theater spawn opencode "say hello" --approval manual
theater ls          # starting → working → idle
theater bus         # the reply, once, whole
```
