# v1.7 — Reliable delivery

An execution plan for the hardening backlog in `docs/17_bug_fixes.md`, merged
with the observation stages in `docs/v1.6_observation.md`.

Those two documents describe one body of work from two angles. `17_bug_fixes.md`
asks "what can go wrong on the wire"; `v1.6_observation.md` asks "what can go
wrong when reading the reply". They share four items and contradict each other
on none, so running them as separate tracks would mean building the same turn
identity twice. This plan supersedes both as the ordering authority; they remain
as rationale.

**Naming.** `v1.6` was never tagged. The eight commits since `v1.5.0` are the
first half of this work. Everything here ships as one release, `v1.7.0`, rather
than splitting a single theme across two tags for reasons that were structural
rather than user-visible.

Verified against the tree, not assumed. This is what the plan builds on.

| Bracketed-paste delivery | `tmux/client.py:213` `deliver_text` | done (`388b447`) |

**Gaps that the plan below closes**, each confirmed by reading the code:

- `deliver_text` checks **nothing** before pasting — not that the pane exists,
  not what is running in it, not `bracket_paste_flag` (its docstring discusses
  the flag; the code never reads it). `client.py:248-256`.
- `Participant.pid` exists in the dataclass (`models.py:46`) and in the schema
  (`schema.py:32`) and is **never written**. The only assignment in the tree is
  `from_row`. Nothing records which process occupied the pane at spawn, so
  nothing can notice that the CLI exited and a shell took its place.
- `Pane` already carries `pane_pid` and `current_command` (`client.py:54,59`),
  so the pre-flight gate's inputs cost no new tmux calls.
- Job completion is positional FIFO with no correlation:
  `observer._answer_turn` takes `store.oldest_running_job_for_target` and hands
  it whatever text ended the turn (`observer.py:623-647`). The backing query
  admits its tie-break is arbitrary (`store.py:235-238`).
- Rescue completes jobs with `state=DONE` and `error_code="turn_end_unseen"`,
  returning `clock.last_text` — the last thing the agent said, whoever it was
  talking to (`observer.py:586-621`, `_finish` at `:666`).
- `HarnessObserver.is_idle_screen` is a single boolean (`observation.py:102`).
  It cannot distinguish "waiting for input" from "showing an approval dialog",
  which is why an injected `Enter` can accept a modal.
- **No test touches real tmux.** `FakeTmux.deliver_text` appends to a list and
  returns (`conftest.py:139`). Every delivery in ~630 tests succeeds
  unconditionally, so delivery failure is currently untestable.

## The invariant chain

The order below is a dependency chain, not a preference. Each stage is only
meaningful once the one above it holds.

```
pre-flight   pane alive · pid matches launch · harness still running · no modal
in-flight    paste, then wait for a receipt against a deadline
post-flight  receipt = the target's own user-record echoing my prompt
             → that single fact proves arrival AND identifies the turn
fallback     positional FIFO — screen-only harnesses, declared, depth-1 forever
```

**Correlation before queueing.** The `Busy` check (`methods.py:308`) allows at
most one outstanding job per pane, and that is precisely what makes positional
FIFO sound today. A queue without correlation deletes the invariant and
produces permanent off-by-one cross-talk: turn N answering prompt N−1 forever,
silently. Queueing is therefore gated on Phase E, enforced by a declared
capability flag rather than by this paragraph.

## Phases

Effort: **S** ≈ hours · **M** ≈ a day or two · **L** ≈ multi-day.

### Phase A — close out the daemon singleton · S · P0 · DONE

The lock is correct but taken too late, and nothing throttles the herd.

1. **Acquire before touching shared state.** `Daemon.__init__` runs
   `load_config`, installs plugins, and constructs `Store` — which runs Alembic
   migrations — and only `start()` then takes the lock (`server.py:85` vs
   `:150`). Two daemons racing therefore both migrate the same SQLite file
   before either loses. Move the acquire to the top of `__init__`. Updates 3-4
   tests that currently expect `start()` to be the raiser; their intent is
   unchanged.
2. **Herd suppression.** Every client that fails to connect spawns its own
   `python -m theater.cli daemon` (`client.py:84`). Five MCP servers noticing at
   once means five processes, four of which pay import + migration to then
   exit. Skip the spawn when `lock.is_free()` is False and go straight to
   `_await_socket()`. Racy by construction — the point is to turn most of the
   herd into waiters, not to be exact.
3. **Decide the unenforced path.** On a filesystem without working flock,
   `lock.py:139` sets `enforced = False` and runs on with a log line. Add a pid
   liveness fallback (`os.kill(pid, 0)` plus start-time comparison) so it
   degrades to a weak check rather than to nothing.

**Exit:** two `theater daemon` invocations racing from a cold start produce one
daemon and one refusal, with exactly one process having opened the database.

**Shipped.** All three, plus a release guard the plan missed: a `__init__` that
raises after acquiring leaves the caller no object to close, so it releases the
lock itself. Item 3 landed as a `ps` probe rather than `os.kill(pid, 0)` —
matching the command text is what makes pid reuse survivable, and start-time
comparison is not portable enough to be worth the second syscall. `is_free`
follows the same fallback, so `theater restart` and the client herd check agree
with `acquire` on filesystems that cannot lock. Residual, documented in the
code: on such a filesystem two daemons starting in the same instant can still
both find an empty pidfile and both win.

### Phase B — instrument before architecting · S · P0 · DONE

Backlog #5. The cheapest item on the page and the one that tells us whether
Phase E earns its cost.

Count per participant and per harness: clean turn ends, rescues
(`turn_end_unseen`), send failures, and — once Phase C lands — pre-flight
refusals. Emit as bus events and surface them in one command
(`theater stats`, or fold into a `theater doctor`).

Rationale: the rescue path is a silent degradation. A harness whose format has
drifted looks *slow*, not *broken*, and today nothing distinguishes "answered
properly" from "we gave up and returned the last thing it said". Ship the
metric first so the later phases can be judged against a baseline instead of an
impression.

**Exit:** `theater stats` reports a rescue rate per harness over the last N
turns, and the number is non-zero for at least one harness (if it is zero
everywhere, Phase E is smaller than we think — that is a useful answer too).

**Shipped, and the numbers are not what the plan assumed.** First run against
this machine's real database, 152 turns:

```
HARNESS       TURNS  CLEAN  RESCUED  FAILED  RUNNING  RESCUE RATE
claude           24     22        0       2        0           0%
codex            15     14        1       0        0           7%
opencode         46     43        3       0        0           7%
vibe             67     66        0       1        0           0%
```

Rescue is not uniform — it is entirely in codex and opencode, the two newest
plugins, and exactly zero in the two oldest across 91 turns. That reframes
Phase E: turn identity is not primarily a job-matching problem, it is two
plugins not recognising their own turn boundaries. Do the per-plugin parsers
first and re-read this table before paying for native turn IDs; the shared
reducer may need nothing.

Also worth noting: 3 crashed sends across all of history, which is the
delivery-failure rate Phase C is aimed at — and it is measured with a
`FakeTmux` that cannot fail, so the real number is a floor, not an estimate.

Two implementation notes. The counts are derived from the jobs table on each
call rather than kept as live counters: `error_code` already records the
distinction, derived numbers survive a restart, and a counter that exists only
to be printed is a thing to keep in sync for nothing. Refusals could not come
from the same place — they happen before a job is reserved, so there is nothing
to record them on — and they now emit a `send.refused` bus event, which also
fixes a smaller problem: a user watching `theater bus` used to see a refused
send as nothing at all.

### Phase C — pre-flight delivery gate · S–M · P0 · DONE

Backlog #1, and the same fix as the known "send into a dead CLI" bug: when a
CLI exits, its pane falls back to a shell, and our paste plus `Enter` executes
the prompt as a shell command. This is the only *irreversible* failure mode in
the backlog — everything else yields a recoverable wrong answer.

1. **Record the launch epoch.** Write `pane_pid` into the existing, unused
   `Participant.pid` column at spawn and at adopt. Both call sites already hold
   a `Pane` (`methods.py:129`, `:153`); the spawner needs it threaded through.
2. **Gate `_send`** on, in order: pane still exists · `pane_pid` equals the
   recorded one · `detect_harness(pane.current_command, pane.pane_pid)` still
   returns the participant's harness. Fail with a distinct, actionable error
   code (`pane_replaced`, `harness_gone`) rather than the generic
   `not_addressable`, and mark the participant dead where the evidence says so.
3. **Modal check, conservative version.** Full classification is Phase F; here,
   consult the existing `is_idle_screen` only as a veto for harnesses that
   declare a modal marker, and leave the rest alone. Explicitly not: treating
   `AWAITING_INPUT` as a gate — that status is a display hint tuned to accept
   false negatives, and using it as a control signal would make a stuck
   `WORKING` pane unreachable.

**Exit:** killing the CLI in a pane and then sending to it fails the send with
`harness_gone` and marks the participant dead, instead of running the prompt in
a shell. Verified in Phase D's rig, not by hand.

**Shipped, with two deliberate deviations.** The gate is
`_check_pane_identity` (`methods.py`), called from `_send` immediately *before*
`human_present` — it is cheaper, it rests on tmux facts rather than a screen
scrape, and there is no point asking who is sitting at a pane that is not the
target's any more. It refuses in four distinct ways:

| evidence | reason | marks dead |
|---|---|---|
| pane is gone from `list-panes` | `pane_gone` | yes |
| pane exists, `pane_pid` differs from the recorded one | `pane_replaced` | yes |
| a *different* known harness is in the seat | `harness_changed` | no |
| no harness found **and** the foreground command is a shell | `harness_gone` | no |

All four raise the new `StaleTarget` (`stale_target`), not `not_addressable` as
the plan said. `NotAddressable` is a permanent property of a tier — an external
participant can never be written to — whereas these mean a working address went
stale, which is a different thing for a caller to react to. All four flow
through Phase B's `_refuse_send`, so `theater stats` counts them.

*Deviation 1: the shell requirement the plan did not specify.* "No harness
detected" alone never refuses. `detect_harness` walks `ps`, and an agent running
its own `bash` tool briefly shows a shell in the foreground; refusing on the
tree walk alone would block legitimate sends to a busy agent. Both halves must
agree — nothing recognisable running *and* a shell at the prompt — before we
call the seat empty.

*Deviation 2: C3, the modal veto, is dropped.* `is_idle_screen` returns a single
boolean and cannot separate "waiting at its input prompt" from "showing an
approval modal". A veto built on it would block ordinary idle panes, which is
the failure mode Phase C exists to avoid creating. Phase F's structured
`ScreenReading` is the right place; the marker is in the backlog.

Marking dead is confined to the two cases where tmux itself is the witness. The
other two rest on a `ps` walk that can fail, and a wrong demotion needs a human
to undo it; the registry's `_evict_pane_holder` already retires the previous
occupant when someone else claims a pane.

The most debatable choice is that the gate **fails open** — if `pane_info`
raises, it logs and lets the send through. A gate that turns a transient tmux
error into an unreachable participant reproduces the harm it was built to
prevent, and the paste immediately after goes through the same tmux and fails
loudly on its own.

22 tests in `tests/test_delivery_gate.py`, including a cross-check that the gate
runs before the presence check and that a refusal reserves no job. 10 of them
fail with the gate call commented out. Verified against `FakeTmux`, which now
models a real pane list; the promised real-tmux proof is Phase D's.

### Phase D — the real tmux rig · M · P0 · DONE

Backlog #4. Everything above is currently hand-verified because no test drives
tmux.

A fixture program that requests DECSET 2004, logs every byte it receives to a
file, and can be told to open a modal. A `@pytest.mark.tmux` suite that skips
when tmux is absent, spawns a real pane running it, and asserts on the received
bytes: paste arrives wrapped in `\e[200~`/`\e[201~`, `Enter` is a separate
event, a multi-line prompt arrives as one paste, and a pane whose program has
exited is refused by Phase C's gate.

Sequencing note: C and D are mutually reinforcing. Build the minimal rig first
(bytes in, bytes logged), land C against it, then grow the rig for E.

**Exit:** CI-skippable suite that fails if delivery semantics regress; the three
"PARTLY VERIFIED" notes in `docs/acceptance.md` become verified or deleted.

**Shipped.** `tests/rig/pane_app.py` is a program that puts its tty in raw
mode, declares DECSET 2004, and appends every byte it receives to a file.
`tests/test_tmux_rig.py` drives 17 tests against it on a real server.

Isolation is by `TMUX_TMPDIR` rather than `-L`. Moving the socket moves the
server, so the tests get a private tmux without threading a socket name through
every call in `theater.tmux.client` — which would have meant testing a
code path that production does not use. The directory sits under `/tmp` because
a unix socket path is capped at 104 bytes on macOS and pytest's `tmp_path`
spends most of that budget before tmux adds its own suffix.

Marked `tmux` and skipped when the binary is absent, rather than deselected by
default. A delivery suite that quietly does not run is worse than none; a CI
box without tmux can still pass `-m "not tmux"`.

What it now proves, none of which any test touched before: a paste arrives
wrapped in `\e[200~`/`\e[201~`; Enter lands *outside* the closing marker;
`enter=False` sends no CR at all; a multi-line prompt is one paste and not two;
`/done Hey! I'm testing ~10 things` arrives verbatim — that is the OpenCode
incident turned into an assertion; two panes pasted concurrently do not receive
each other's text; `new_window -e` reaches the program's environment;
session-scoped `list_panes`, `kill_pane` and `capture-pane` do what the code
assumes. Phase C's gate is exercised against real panes for all four verdicts.

Reverting `deliver_text` to `send-keys -l` — the implementation that caused the
incident — fails six of the seventeen. That is the check on the suite itself.

Two findings worth keeping. tmux rewrites an embedded newline as CR inside the
paste, so a multi-line prompt carries the same byte Enter does; it is only safe
*because* it is bracketed, which is an argument for the paste design rather
than against it. And a program wrapped in non-interactive `sh -c` is never put
in its own process group, so `#{pane_current_command}` reports the wrapper for
the whole life of the pane — which makes that wrapper a faithful stand-in for a
dead CLI and a useless one for a live one. An interactive shell does create the
group, which is why a hand-started `claude` shows up as `claude`.

The "PARTLY VERIFIED" note this phase was meant to retire was in
`theater/tmux/client.py`, not `docs/acceptance.md`. It has been replaced with a
statement of what the rig covers.

### Found while capturing — the 64 KiB socket ceiling · S · P0 · DONE

Not in the plan. It turned up while scripting the Phase E captures: a
`bus.tail` deep enough to find four transcript paths killed the client with
`ValueError: Separator is not found, and chunk exceed the limit`.

Neither end of the socket passed a `limit` to asyncio, so both kept the 64 KiB
default — about ten assistant turns. `read_transcript` returns whole sessions
by design, `bus.tail` returns whatever depth it is asked for, and a prompt may
carry a pasted file; all three cross that ceiling in ordinary use. This is the
most likely explanation for the oldest complaint in `17_bug_fixes.md`, that
Theater "sometimes responds and sometimes errors" — every MCP server holds one
`DaemonClient` for the life of an agent, and the failure was not clean.

Two things were wrong, and the second is the one that made it persistent.
`readline` reports an overrun as a bare `ValueError`, which no caller caught,
so it escaped the `except (TimeoutError, ConnectionError, OSError)` that would
have dropped the connection. And an overrun leaves the stream mid-message, so
the connection stayed in use while desynchronised: one oversized reply, and
every later call on that connection read someone else's bytes.

**Shipped.** `MAX_MESSAGE_BYTES = 64 MiB` in `protocol.py`, alongside the two
readers both ends now share. A limit is kept rather than removed because it is
what caps how much a peer that never sends a newline can make the other end
buffer. `read_message` raises `MessageTooLarge`, a `ConnectionError` subclass,
which routes an overrun into the drop-and-reconnect machinery that already
exists. The daemon answers an oversized *request* with `too_large` and drains
the rest of the line instead of hanging up, so one absurd prompt does not cost
an agent its session. Both readers use `readuntil`, not `readline`: `readline`
clears its entire buffer on overrun, which would discard a pipelined message
that had already arrived behind the oversized one — the unit test caught that,
the end-to-end test did not.

Nine tests in `tests/test_message_size.py`; six fail with the limits reverted.

### The captures · DONE

One real injected round-trip per harness, sent through the daemon exactly as
an agent would, with the transcript snapshotted either side. The prompt was
"reply with exactly CAPTURE-<H>-OK and nothing else", so the turn is one user
record and one assistant record with no tool calls in between — the smallest
turn each CLI can produce, which is the clearest place to see its boundary.

**Every harness has native turn identity.** This was the open question behind
E1 and the answer is better than assumed:

| harness | turn starts | turn ends | native id |
|---|---|---|---|
| codex | `event_msg/task_started` | `event_msg/task_complete`, or `turn_aborted` | `payload.turn_id`, identical on both |
| claude | `user` record | `assistant` with `stop_reason: "end_turn"` | `requestId`, plus the `parentUuid` chain |
| opencode | `message` row, `role=user` | `part` row with `{"reason":"stop"}` | assistant `message.id`, which every part references |
| vibe | `user` record | assistant record, turn-end flag | none observed |

Two of them go further and record *parentage*, not just identity. Claude's
assistant record chains `parentUuid` back through the attachment to the user
record that caused it; OpenCode's assistant message carries `parentID` naming
the user message. Codex brackets the whole exchange inside one `turn_id`.

That materially changes Phase E2. A hash of the prompt was designed as a way
to correlate a reply with the send that caused it, for want of anything
better. Three of four harnesses *already publish that correlation*, and a
native id beats a content hash on every axis — it cannot be defeated by the
CLI reformatting the prompt, by two identical prompts, or by a system reminder
wrapped around it. The hash belongs where there is no native id, which so far
is vibe alone.

Also worth recording: codex's `task_complete` carries `last_agent_message`,
and opencode's terminal part carries `reason`, so both boundaries are
self-describing — neither needs the accumulator to recover the reply text.
Claude's does not, which is exactly the case E1's accumulator is for.

Fixtures from all four are in `tests/fixtures/`.

### Found while capturing — the observer follows the wrong session · P0

The vibe capture failed, and the way it failed is the most valuable thing on
this page.

The prompt was delivered. `capture-pane` on `%98` shows it typed into the
composer and shows `CAPTURE-VIBE-OK` in the reply. But `jobs.await` sat at
`running` for the full 120s, zero new records were seen, and the participant
is *still* marked `working`. The observer was reading a different file: the
transcript of the vibe session running this very task, in the same directory
and outside tmux entirely.

`TranscriptSource.refresh()` re-searches by cwd and ignores the session id it
already knows (`harness/source.py:237`). It was written for vibe's session
rotation, where following the newest session in a directory is correct. With
two vibe sessions in one directory it binds to whichever wrote last — and it
persists the new id into the registry, so the record is not merely stale but
actively wrong. This participant rebound twice: pane `%98` really runs session
`0fee0d2a`, the registry said `13f7192a`, and by the end it held `91ca0175`.

Consequences, all of which are on the backlog under other names: a job that
never completes though the target answered; a participant stuck at `working`
forever; `read_transcript` returning someone else's conversation. It is a
plausible cause of a share of the codex/opencode rescue rate measured in
Phase B, since those runs also had several sessions per directory.

Not fixed here. It belongs with E — relocation should be a declared plugin
capability, and rebinding should require session identity rather than a shared
cwd — and it is listed among the dangerous changes to discuss.

### Phase E — delivery receipt and turn identity · M–L · P0

Backlog #2 and #7, plus `v1.6_observation.md` stages 1-2. The heart of the work,
deliberately last among the P0s because it is the only one that cannot be
undone cheaply.

1. **Turn identity.** `Event.turn_id` from the harness's native id where one
   exists; a persistent per-participant `TurnAccumulator` replacing the
   batch-local `reply` variable (`observer.py:371`), so a boundary landing in
   the next poll does not return an empty result and a multi-block answer is
   not truncated to its last block. Completion dedup keyed on `turn_id`, since
   Claude admits one native message can produce several boundaries
   (`plugins/claude.py:21`).
2. **Receipt.** Store a normalized hash of the prompt at send. The job goes
   `pending → running` only when the target's own transcript shows a `user`
   record containing it. No match inside a deadline (~5s) → finish
   `not_delivered`. One observation proves transport, UI acceptance, and
   submission, and identifies the turn — which is why it replaces both the ack
   and the correlation, rather than being a third mechanism.
3. **What this retires.** Positional FIFO for transcript harnesses; the human
   turn stealing a peer's job and disclosing the operator's words (a human's
   keystrokes match no hash); and the rescue path returning the last thing said
   as if it were the answer — rescue becomes `not_delivered` or a genuine
   timeout, never a fabricated success.

**Exit:** two agents exchanging ten messages, with a human typing into one of
the panes mid-conversation, produce ten correctly-paired replies and zero
rescues; the human's turn resolves nothing.

### Phase F — declared capabilities, then queueing · M · P1

Only once E holds.

- `correlation: "receipt" | "positional"` declared on the plugin, not inferred
  at runtime (a version bump gets inference wrong). Backlog #12.
- `ScreenReading{kind, confidence}` replacing the boolean `is_idle_screen`,
  which upgrades Phase C's conservative modal veto into a real one.
  `v1.6_observation.md` stage 4.
- Observer health: `DriverHealth`, an `unknown` activity state, watcher restart
  with bounded backoff instead of permanent retirement (`observer.py:189`).
  Stage 5, and the structural half of backlog #10's drift canary — Phase B is
  the alarm, this is the diagnosis.
- Queue depth limits and loop detection, `positional` harnesses pinned at
  depth 1. Backlog #9.

## Deferred, with rationale

- **#8 sender leases.** The `Busy` check already gives depth-1 exclusion.
  Leases answer "which sender owns this pane", a question that only becomes
  distinct from presence once a queue exists. Ships with Phase F or not at all.
- **#11 delivery envelope.** P2, and honest about its scope: it resists
  confusion, not injection. Worth doing, worth doing after correctness.
- **#10 canary, threshold half.** The alarm is Phase B; per-plugin schema
  self-checks land with Phase F's health work.
- **Capability-scoped control ops** and **signed provenance** stay cut, for the
  reasons in `17_bug_fixes.md` — same uid, same machine, unix socket, and an
  LLM cannot verify a signature.

## Risks

- **Phase E is the one that can regress everything.** It changes how every job
  completes. Mitigation: it lands after D, so the rig exists; and behind the
  `correlation` flag, so a harness can be moved back to positional in one line.
- **Fixture corpus.** Stage 6's contract tests need real transcripts from all
  four CLIs, including drifted and truncated ones. Only the user can capture
  those; it is the long pole on test quality and should start being collected
  during Phase B.
- **Phase B could show the rescue rate is near zero.** Then E shrinks to turn
  identity plus human-turn attribution, and the receipt becomes optional. That
  is the point of measuring first.
